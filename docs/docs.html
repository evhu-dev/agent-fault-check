agent-fault-check (afc) Docs

Everything you need to install afc, write your first chaos-spec.yaml, wire a deterministic PR merge gate in GitHub Actions, and troubleshoot failures.

1. Quickstart & Installation

afc ships as a single static binary for Linux (amd64, arm64) and macOS (arm64, amd64), plus multi-arch Docker images.

Install OSS Core (Apache-2.0)

VERSION="v0.1.0"
OS=$(uname -s | tr '[:upper:]' '[:lower:]')
ARCH=$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')
TARBALL="afc_${VERSION#v}_${OS}_${ARCH}.tar.gz"

curl -fsSLO "https://github.com/evhu-dev/agent-fault-check/releases/download/${VERSION}/${TARBALL}"
curl -fsSLO "https://github.com/evhu-dev/agent-fault-check/releases/download/${VERSION}/checksums.txt"
grep " ${TARBALL}$" checksums.txt | shasum -a 256 -c -
tar -xzf "${TARBALL}" afc
sudo install -m 0755 afc /usr/local/bin/afc
afc version

2. How the Proxy & Runner Work

For each scenario in chaos-spec.yaml, afc executes a deterministic lifecycle:

  1. Fixture Setup (optional): Runs fixture.setup_argv to seed or reset disposable test state.
  2. Local Fault Proxy: Starts an ephemeral HTTP reverse proxy on 127.0.0.1 forwarding to proxy.upstream_url.
  3. Agent Execution: Spawns agent.argv in its own process group with injected environment variables so your agent routes tool calls through the proxy.
  4. Fault Injection & Tracing: Matches configured HTTP requests, injects faults deterministically, and records a full call timeline.
  5. Quiesce & Assertions: Optionally runs fixture.quiesce_argv, then verifies database, Redis, HTTP state, retry, and tool-budget assertions.
  6. Teardown & Reporting: Always runs fixture.teardown_argv (even on timeout), redacts secrets from logs, and writes Console / SARIF / JUnit outputs.

Environment Variables Injected Into Your Agent & Fixture

VariableDescription
TOOL_API_BASE_URLBase URL of the local fault-injection proxy (e.g. http://127.0.0.1:54321). Point your agent's tool API client here.
AFC_RUN_IDUnique ID generated per scenario execution. Use it to scope test rows/keys cleanly across parallel runs.

3. chaos-spec.yaml Reference

Below is a complete example showing both OSS and Pro options:

version: "1.0"
name: "checkout-recovery"

agent:
  argv: ["python3", "run_agent.py"]
  timeout_seconds: 30
  env:
    AGENT_MODE: "idempotent"
  env_allowlist: ["OPENAI_API_KEY"]   # Optional: pass specific host env vars through

fixture:
  setup_argv: ["python3", "fixture.py", "setup"]
  quiesce_argv: ["python3", "fixture.py", "quiesce"]
  teardown_argv: ["python3", "fixture.py", "teardown"]

proxy:
  transport: "http"
  listen_addr: "127.0.0.1:0"          # :0 picks an ephemeral free port
  upstream_url: "http://127.0.0.1:8000"
  upstream_timeout_ms: 5000

state_stores:
  orders:
    type: "postgres"
    dsn_env: "AFC_TEST_POSTGRES_DSN"
  cache:                              # Pro / Team
    type: "redis"
    url_env: "AFC_TEST_REDIS_URL"
  ledger:                             # Pro / Team
    type: "http"
    base_url: "http://127.0.0.1:8000"

scenarios:
  - id: "duplicate-write-on-502"
    prompt: "Create a $49.00 order for customer cust_123."
    abort_after_tool_calls: 5         # Hard-kill runaway agent loops
    faults:
      - id: "lose-first-response"
        strategy: "commit_then_fail"
        match:
          method: "POST"
          path: "/api/v1/orders"
          call: 1
        success:
          status: 201
          means_durable_commit: true
        inject:
          kind: "http_error"          # or "timeout" with hold_ms: 2500
          status: 502
    assertions:
      - type: "operation_attempts"
        fault: "lose-first-response"
        correlation_header: "X-Operation-ID"
        min_after_injection: 1
      - type: "sql_row_count"
        store: "orders"
        query: "SELECT COUNT(*) FROM orders WHERE run_id = $1 AND customer_id = $2"
        args: [{ runtime: "run_id" }, "cust_123"]
        expected: 1
      - type: "redis_key_absent"      # Pro / Team
        store: "cache"
        key: "order:lock:{{run_id}}"
      - type: "http_state_count"      # Pro / Team
        store: "ledger"
        path: "/state/orders?run_id={{run_id}}"
        expected: 1
      - type: "max_tool_calls"
        match: { method: "POST", path: "/api/v1/orders" }
        max_calls: 3
Runtime placeholders: In SQL args, pass { runtime: "run_id" } (parameterized safely via $1). In Redis keys/patterns and HTTP state paths, use {{run_id}}.

4. Fault Injection Strategies

StrategyBehaviorWhat Bugs It Catches
commit_then_fail Forwards the request to upstream, verifies upstream returned success.status (durable commit), then returns an injected http_error (e.g. 502) or timeout (hold_ms) to the agent. Duplicate charges, double orders, missing idempotency keys when retrying after ambiguous failures.
fail_before_upstream Immediately returns an injected http_error (e.g. 500 / 503) without calling upstream. Broken saga rollbacks, leaked locks/reservations, unhandled downstream errors.
malformed_json Returns HTTP 200 with truncated/corrupted JSON body to the agent. Unhandled parse crashes, infinite retry loops on corrupt tool payloads.

5. State & Budget Assertions

Assertion TypeTierPurpose
sql_row_count OSS + Pro Runs a parameterized PostgreSQL SELECT COUNT(*) query and asserts exact expected count.
operation_attempts OSS + Pro Verifies the agent actually retried after a fault (using correlation_header and min_after_injection), preventing false passes from agents that silently abort.
max_tool_calls OSS + Pro Caps matching proxied HTTP calls (max_calls) to catch retry storms and token-burning loops.
redis_key_absent Pro / Team Asserts a Redis key (e.g. distributed lock) does not exist after the run.
redis_key_count Pro / Team Uses deduplicated Redis SCAN on pattern and asserts exact expected key count.
http_state_count Pro / Team Queries an HTTP state endpoint returning a JSON integer (e.g. 1) and asserts exact expected count.

  with:
    spec-path: "chaos-spec.yaml"
    version: "v0.1.0"
    report-mode: "console"

Pro / Team Workflow (SARIF Code Scanning + JUnit) PRO / TEAM

permissions:
  contents: read
  security-events: write

steps:
  - uses: actions/checkout@v4

  - name: Run agent-fault-check Pro
    id: afc
    uses: evhu-dev/agent-fault-check@v0.1.0
    with:
      spec-path: "chaos-spec.yaml"
      version: "v0.1.0"
      release-repository: "evhu-dev/agent-fault-check-releases"
      license-key: ${{ secrets.AFC_LICENSE_KEY }}
      report-mode: "both"

  - name: Upload SARIF to GitHub Code Scanning
    if: always() && steps.afc.outputs.sarif-file != ''
    uses: github/codeql-action/upload-sarif@v3
    with:
      sarif_file: ${{ steps.afc.outputs.sarif-file }}

8. SARIF 2.1.0 Rule Reference PRO / TEAM

Each SARIF finding includes deterministic fingerprints, remediation markdown, and execution timelines for GitHub Security / PR annotations:

Rule IDNameMeaning
AFC101PersistentStateMismatchPost-run Postgres, Redis, or HTTP state did not match expected count (duplicate write or leaked rollback state).
AFC102MissingRetryAfterFaultAgent did not retry after an injected fault using the expected correlation header.
AFC103ToolCallBudgetExceededAgent exceeded max_tool_calls or hit abort_after_tool_calls.
AFC104DeclaredFaultUnfiredA declared fault rule never matched any proxied HTTP request.
AFC105AgentExecutionFailedAgent process exited non-zero or exceeded timeout_seconds.
AFC201ChaosRunnerInfraErrorFixture hook, state store connection, proxy drain, or upstream verification error.

10. Troubleshooting

AFC104: Declared fault never fired

Your agent did not send a request matching faults[].match through the proxy. Check:

  • Your agent's HTTP client reads TOOL_API_BASE_URL as its base URL (not hardcoded localhost:8000).
  • match.method (e.g. POST), match.path (exact path without query string), and match.call (1-indexed) match what appears in the call timeline with --verbose.

commit_then_fail fails with upstream status mismatch (AFC201)

commit_then_fail verifies the upstream API actually committed (returned success.status, e.g. 201) before injecting the fault. If your upstream returns 200 instead of 201, update success.status: 200.

report-mode 'sarif' is not supported by the public OSS release

In the GitHub Action, SARIF and JUnit require the Pro binary. Set release-repository: "evhu-dev/agent-fault-check-releases" and provide license-key: ${{ secrets.AFC_LICENSE_KEY }}.

entitlement error: license key rejected by Polar (HTTP 404)

Verify the key has no trailing whitespace/newlines, belongs to an active Pro or Team subscription in the Polar Customer Portal, and that your runner has outbound HTTPS access to api.polar.sh.

Postgres or Redis connection refused in CI

Ensure your CI service container has a healthcheck (e.g. pg_isready / redis-cli ping) and that dsn_env / url_env matches the exact environment variable exported to the step.

11. Frequently Asked Questions

Does agent-fault-check work with any AI agent framework or language?

Yes. afc is completely framework- and language-agnostic. It launches your agent via agent.argv (Python, TypeScript/Node, Go, Java, etc.) and intercepts standard HTTP tool calls via TOOL_API_BASE_URL. It works with LangGraph, CrewAI, OpenAI Agents SDK, Anthropic SDK, AutoGen, or custom loops.

Does afc call my LLM or replace my LLM mocks?

No. afc only proxies the HTTP tool APIs you point at TOOL_API_BASE_URL. You can run against a real LLM or a deterministic stubbed LLM depending on your CI budget.

Should I point afc at a production database?

Never. Always run afc against disposable local or CI service containers (such as GitHub Actions Postgres/Redis service containers or local Docker Compose).

Does the CLI collect telemetry or upload my code/prompts?

No. Both afc and afc-pro collect zero usage telemetry and never transmit prompts, source code, HTTP payloads, or database contents. Pro license validation contacts api.polar.sh solely to verify your license key.

What is the difference between the OSS and Pro binaries?

The OSS binary (afc, Apache-2.0) supports up to 3 scenarios per run, all HTTP fault strategies, PostgreSQL + budget assertions, and console output. The Pro binary (afc-pro) adds unlimited scenarios, Redis and HTTP state assertions, and SARIF 2.1.0 + JUnit XML reporting.

How do billing, upgrades, cancellations, and refunds work?

All billing is handled by Polar.sh (Merchant of Record). You can upgrade, download invoices, or cancel anytime in the Polar Customer Portal. New Pro and Team subscriptions include a 14-day refund policy—see Commercial Terms & Refunds.
